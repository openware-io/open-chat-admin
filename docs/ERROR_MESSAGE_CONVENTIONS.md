# Admin 错误提示规范

状态：生效。适用范围：`gv_chat_admin` 的所有页面、API 模块和后续迭代需求。

## 目标

- 面向管理员的提示必须使用简体中文、业务化且可执行的描述。
- 不得向页面直接展示后端 `message`、异常文本、英文技术术语、堆栈、URL、请求参数或内部实现信息。
- 后端稳定错误码是前端提示的唯一业务识别依据；HTTP 状态码只用于通用兜底。

## 唯一入口

- 网络请求错误必须由 `src/utils/adminErrorMessage.js` 解析和展示。
- API 调用需要明确操作语义时，必须通过 Axios 配置 `errorContext` 传入动词短语，例如“创建发布草稿”“撤回发布”。提示格式统一为：`<操作>失败：<可执行原因>`。
- 页面可直接显示本地表单校验、用户取消和纯前端文件校验提示；不得在 `catch` 中读取或展示 `error.message`、`response.data.message`。

## 错误码契约

- 新增或调整管理接口的失败分支时，后端必须返回稳定的 `code`；禁止以前端匹配英文 `message` 作为业务分支。
- 新错误码必须同时登记到 `ERROR_CODE_MESSAGES`，提供简体中文、无需内部上下文即可理解的提示。
- 业务提示应说明管理员下一步可执行的动作，例如“请刷新后重试”“请使用已配置的官方分发地址”。禁止使用“未知错误”“请求失败”等无行动信息作为业务错误码提示。

## 文案与展示

- `error` 用于操作失败；`warning` 用于操作前校验或风险提醒；`success` 仅用于确认已完成；`info` 仅用于非阻断说明。
- 一次请求只允许展示一次错误提示。网络层已提示后，页面不得重复提示。
- 认证失效、权限不足、并发冲突、资源不存在、限流、网络失败和超时必须使用统一兜底文案。
- 需要定位时，由后端日志和 `requestId` 完成；页面不得暴露 `requestId` 以外的技术细节。

## 验证与评审

- 提交前执行 `npm run validate:error-messages` 和 `npm run build`。
- 校验会禁止在页面中直接把异常对象或响应 `message` 传给 `ElMessage.error`。
- 代码评审必须核对：后端稳定错误码、前端映射、操作上下文、无重复提示、无技术原文泄露。
